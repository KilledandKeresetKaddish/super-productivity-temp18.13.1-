## 三、"削头" BUG — 根因（已实证）

本次拿到了 SP 仓库源码（此前多轮无法直读），直接读到了共享组件
`src/app/features/schedule/schedule-event/schedule-event.component.scss` 的真身：

```scss
.title {
  --title-padding-y: 6px;          // ← 罪魁祸首①：上下各 6px 内边距
  padding: var(--title-padding-y) 6px;
  line-height: 1.4;
  max-height: 100%;                // ← 罪魁祸首②：把 .title 盒子钳到条子高度
  overflow: hidden;
  .title-text {
    display: -webkit-box;          // 行钳制（line-clamp）路径
    -webkit-line-clamp: var(--title-line-clamp, 1);
  }
}
:host.very-short-event .title {
  padding: 1px 6px var(--s-quarter);  // ← very-short 变体只有 1px，所以它从不削头
}
```

**机制**：插件把条子压到 16px（--tarot-strip-h）、行高定为 14px，但从未清掉
`.title` 的 6px 纵向 padding。于是 14px 的文字行被垫片下推 6px，从条内
y≈7 排到 y≈21（条子只有 16px 高），溢出的部分被 overflow:hidden 裁掉。
Chromium 表现为裁下缘；Firefox（用户实机）视觉上呈"削头/像上移 ~8px"。
`--title-line-clamp` 是组件 JS 用 ResizeObserver 按 (clientHeight − paddingTop −
paddingBottom)/lineHeight 实时算的 inline 变量 —— 同一个 6px 垫片也在污染这笔账。

**为什么只有部分日期中招（谜底）**：削不削头由事件是否带 `very-short-event`
类决定 —— 预估时长 ≤15 分钟的任务走 very-short 路径（padding 1px，不削）；
**带真实时间预估（>15min）的任务走普通路径（padding 6px，必削）**。
用户日历里 7–10、13 号恰好是排了带预估任务的日子；远期无预估的提醒类任务
默认按 10 分钟处理 → very-short → 看起来"正常"。与 v1.6 探针记录
（11 号 very-short 正常、7–10 号 span 34/56 削头）完全吻合。
"时好时坏"的错觉 = 不同日子任务预估不同，而非渲染不稳定。

**旧假设归档**：H1 假性滚动（v1.6 已出局）；H2' 幽灵几何（6px margin-bottom
确实存在、v1.7 已清，但不是削头主因）；H3 绘制伪影（本轮出局 —— 几何测量
直接命中位移，用户"命中随视觉走"观察也指向真实位移）。v1.7 的 7f
translateZ(0) 层隔离试验已随 v1.8 删除。

## 四、修复内容与验证（v1.7 → v1.8）

**CSS 变更（全部在月视图作用域内，周/日视图不受影响）**：

- 新增 7d' 段：`schedule-event.month-schedule-event .title`
  → `--title-padding-y: 0px; padding: 0; margin: 0; max-height: none;
  position: static; transform: none; align-self: center`（position/transform
  是给 split-continued 变体兜底的，其原生 .title 为 absolute + translateX）。
- 新增：`… .title .title-text` → `display: block; max-height: none; padding: 0; margin: 0`
  （关掉 -webkit-box 行钳制路径，走标准单行省略号）。
- 删除 7f（translateZ(0) 试验段）。
- manifest 1.8.0。JS 未改。

**验证方法（真实环境自动化，非纸面推演）**：本仓库源码 + `ng serve` 跑起
v18.13.1 前端，Playwright 造数（带 3h/4h/5h 预估的任务、10 分钟短任务、带
具体时间任务、超预算日、跨月任务），切月视图，先量原生、再注入 v1.7 与
v1.8 的 plugin.js 各量一遍。每条细条量 `.title-text` 相对条子的
top/bottom（getBoundingClientRect，对 transform 不盲）：

| 状态 | 文字行相对条子 | 结论 |
| --- | --- | --- |
| 原生（无主题） | 完整在条内 | 原生无此 BUG，纯主题交互问题 |
| v1.7 | top +7 / bottom **+5（溢出）**，8 条里 7 条削 | 复现，唯一幸免的是 very-short |
| v1.8 | top +1 / bottom −1，**0 条削** | 修复，含 beyond-budget / split-start / ScheduledTask / 跨月 |

## 五、残余风险与后备方案

- 验证跑在 Chromium（容器无 Firefox）；但 v1.7 的 Chromium 复现与用户
  Firefox 实机现象同源（同一几何位移，只是裁切方向观感不同），修复清的是
  位移本身，两引擎同治。iOS WebKit 同理。
- 若实机仍见异常，先跑只读探针（贴控制台）确认 padding 是否真为 0：
  `document.querySelectorAll('schedule-event.month-schedule-event .title').forEach(t=>{const c=getComputedStyle(t);console.log(t.textContent.trim().slice(0,10),c.paddingTop,c.paddingBottom,c.lineHeight,c.maxHeight)})`
  padding 非 0 → 说明该安装的 CSS 未更新（旧 zip 缓存），重装插件；
  padding 为 0 仍削 → 带截图 + 上述输出开新窗口。
- 8 号"两条之间异常间距"未在 v1.8 环境复现（各条严格 16+1px 堆叠）；大概率
  是削头造成的视觉误判，若独立复现再单独立案。
- 月末格子里最后一条被格子下缘截半属原生滚动容器行为（格内可滚），非 BUG。
